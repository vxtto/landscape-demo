## 0:00—3:20｜开场与路线

### Slide 1｜开放生态的老规矩，从来没有过时（0:45）

要说清：

- 今天不是项目盘点，而是回答开放在模型与 agent 时代要开放什么。
- 技术变化很快，但开放入口、公开过程、渐进式信任仍然有效。

开场句：

> Agentic AI 改变了谁在写代码，也改变了什么东西需要被开放。今天想讨论的是：技术对象变了以后，开放生态的老规矩还剩下什么？

### Slide 2｜今天要回答的，不是“谁更火”（0:45）

五部分是一条递进关系：

1. 用 landscape 看结构变化；
2. 用 Apache 看底层系统与跨组织治理；
3. 用 InclusionAI 看多层参与路径；
4. 用开放模型许可证看传统工具的边界；
5. 回到 Community >>> Code。

### Slide 3｜三张图，一个系统（1:50）

指图顺序：

1. Agent Infra：agent 怎么行动；
2. Model Infra：系统怎么托住行动；
3. Large Models：能力从哪里来、开放边界在哪里。

只讲结构，不念项目。若切动态页面，只切换三个 view 或点开一个项目。

转场：

> 图会持续变化，所以真正需要解释的不是这次加了谁，而是我们如何避免把一时热度误判成生态趋势。

## 3:20—6:55｜生态变化与方法

### Slide 5｜README 正从“给人读”变成“给 agent 执行”（1:35）

三个数字：

- 扫描 460 个仓库；
- 24 个项目入图，2 个历史参照；
- 入图项目中约 79% 可被 agent 直接消费，约 92% 创建于 2025 年以后。

结论：

> 开源资产开始封装顺序、约束和经验。README 不再只是说明书，而在成为轻量的 agent 接口。

转场：

> 当 agent 越来越像同事，它脚下依赖的系统反而越来越像经典的分布式基础设施。

## 6:55—13:15｜Apache 的生态位置

### Slide 6｜Apache 在系统主干上（0:20）

只做转场：

> 如果只看 Agent UI 和 Framework，Apache 似乎不在中心；视线下移到数据、计算、事务、调度和治理，位置就完全不同。

### Slide 7｜Apache 的规模是一套长期协作能力（2:00）

官网当前口径：

- 290+ projects；
- 1,300+ annual releases；
- 10,000+ committers；
- 1,190+ members。

可补充但必须区分：

- FY2025：295 projects、9,905 committers、1,147 members、1,310 releases；
- GitHub `apache` org 在 2026-07-29 有 3,148 个公开仓库，其中 648 个归档。

结论：

> Apache 的规模不只是仓库数量，而是项目、身份、发布和治理共同形成的基础设施信用。

### Slide 8｜Apache 在关键层集中出现（2:00）

当前 Model Infra 入图选择：

- Apache 项目 6/57，占 10.5%；
- Data · Governance 4/7，占 57.1%；
- Data · Integration 1/3；
- Compute & Scheduling 1/4。

项目：Iceberg、Hudi、Paimon、Gravitino、Airflow、Spark。

核心句：

> Agent 越像同事，底层越像一套分布式系统；这正是 Apache 最熟的地方。

### Slide 9｜蚂蚁参与的四个 Apache 项目（2:00）

不要讲项目百科，按生产问题讲：

- Fory：状态与消息的高性能跨语言序列化；
- GeaFlow：实时变化的关系、知识与行为计算；
- Seata：跨服务副作用、一致性与补偿；
- Celeborn：计算与数据移动解耦。

收束：

> 它们不一定是 Agent 发布会的主角，但决定系统能不能从“会跑一次”变成“可持续运行”。

## 13:15—17:25｜InclusionAI 的参与式技术栈

### Slide 10｜开放是一条参与路径（0:20）

> Apache 展示跨组织基础设施如何长期治理；InclusionAI 想回答的是，模型与 agent 时代怎样让开发者从不同层真正进入。

### Slide 11｜Models → Training → Runtime（2:10）

按层讲：

- Models：Ling、LLaDA、Ming；
- Training：AReaL、AReno、TwinFlow；
- Runtime：AWorld、AEnvironment、Avernet。

重点不是项目数量，而是贡献梯度：没有大规模训练资源的开发者，仍然可以进入环境、工具、评测与运行时。

口径提醒：AReaL 主仓库在 `areal-project/AReaL`。这里讲 InclusionAI 参与和构建的技术栈，不说成全部项目都在 `inclusionAI` org。

### Slide 12｜把开放做成组织默认值（1:40）

截至 2026-07-28：

- 58 个公开仓库；
- 10,753 stars；
- 26 个 Apache-2.0、19 个 MIT；
- 45/58 为 Apache-2.0 或 MIT；
- 13 个未识别或未声明，需要人工核验。

转场：

> GitHub license 字段适合软件仓库。面对权重、数据、训练代码和文档，它只告诉了我们法律层的一部分。

## 17:25—24:15｜许可证只解决一半问题

### Slide 13｜Rights ≠ Materials ≠ Participation（0:20）

向观众提问：

> 一个模型允许商用，但没有训练数据说明、没有训练代码、没有关键文档，我们应该把它叫做“开放”吗？

### Slide 14｜模型至少要看两层（2:00）

左边：许可证回答“可以做什么”。

- 使用、修改、分发；
- 专利授权；
- 署名、责任与用途边界。

右边：开放度回答“实际拿到了什么”。

- 权重、代码、数据信息；
- 训练方法、文档、评测；
- 是否存在真实修改路径。

结论：

> 许可证解决法律上能不能，开放度解决工程上和研究上能不能。

### Slide 15｜五套方案不是同一类工具（2:30）

定位顺序：

- Apache-2.0：成熟软件许可证；
- OpenMDW 1.1：面向 Model Materials 的宽松许可证，不强制材料完整；
- ModelGo：8 个可组合许可证变体；
- MOF：模型开放完整度框架，不是许可证；
- OSAID：开放 AI 定义，不是许可证。

最后指向“选择原则”一行：

> 先识别对象，再分别验证法律权利、材料完整度和参与路径。

### Slide 16｜Top 50 模型许可证快照（2:00）

本仓库 2026-07-28 选择集：

- 24/50 提供公开权重；
- 公开权重模型中 MIT 9、Apache-2.0 8、其他 7；
- 17/24，即 70.8%，使用 MIT 或 Apache-2.0。

口径提醒：

- 不是全球市场份额；
- 公开权重不等于符合 OSAID 或 MOF 的完整开放。

转场：

> 如果许可证不能独自解决材料完整度与参与问题，答案就必须回到社区怎样组织协作。

## 24:15—30:00｜Community >>> Code

### Slide 17｜代码是结果，社区是系统（0:20）

> CommunityOverCode 不是说社区比代码更温柔，而是社区决定代码能否共同维护、争议能否处理、下一代贡献者能否进入。

### Slide 18｜入口、过程、信任（2:40）

三个机制：

1. 可发现的贡献入口：从 issue、文档、测试扩展到模型卡、数据卡、权重说明、prompt、skill、tool、environment 与 evaluation；
2. 可审查的公开过程：设计、异议、review、发布与安全处置留下记录；
3. 随贡献积累的信任：身份与权限来自持续贡献，而不是雇主或头衔。

核心句：

> 老规矩不是把 20 年前的流程原样复制，而是保留它解决的问题，再把对象从 code 扩展到 model、data、tool、evaluation 与 agent behavior。

### Slide 19｜结尾（1:20）

建议完整口播：

> Agentic AI 改变了谁在写代码，也改变了什么东西需要被开放。Apache 给我们的不是一套怀旧规则，而是一套跨组织协作的工程。InclusionAI 这样的参与式技术栈说明，开放要从单个仓库延伸成多层入口。开放模型许可证让权利更清楚，但材料完整度和参与路径仍要由定义、文档和社区补上。
>
> 所以，开放生态的那些老规矩没有过时：让入口透明，让过程可审查，让信任随贡献积累。真正需要更新的，是把它们从 code 延伸到 model、data、tool、evaluation 和 governance。
>
> Community >>> Code，不是因为代码不重要，而是因为社区决定代码、模型与 agent 能走多远。
